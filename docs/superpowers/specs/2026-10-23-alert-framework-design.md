# CBoK Alert：来源、检测、通知与模型机制设计（评审稿）

日期：2026-10-23

## 1. 目的与首版范围

增加腾讯新闻来源，并把来源接入、来源契约检测、通知渠道和模型接入拆成可独立扩展的机制。

用户已明确：这次先打通板块抓取和变化检测；主题筛选及模型分析流程留后续。模型机制本次提供配置、统一调用接口和现有后端适配，不把模型分析自动串入新来源。

首版包含：

- 腾讯新闻要闻、财经、科技板块的列表抓取，以及文章详情提取能力。
- 每个来源可配置多个有固定 ID 的检测条目，周期检查是否违反明确预期。
- 异常与恢复状态持久化，并经统一通知机制交给邮件渠道；其他渠道以后按相同接口接入。
- 可配置模型配置项，提供 G4F、DeepSeek 和其他 OpenAI 兼容服务的接入方式。
- 手动采集、执行检测的入口及显式周期任务入口，方便开发和部署验证。

本次不做前端页面、主题筛选、新闻价值判断、自动问答/摘要，以及其他通知渠道的实际适配。

第三方页面或内部接口无法保证永不变化。本设计保证的是：使用的解析契约可以描述、验证，并在不满足预期时记录证据和通知。

## 2. 已核实的现状

- `AlertManager` 构造时绑定 Google 登录、DeepSeek 和邮件；新来源检测不得复用这条初始化链。
- 当前 Article 必须属于 Topic，且 URL 全局唯一，不宜用来存储未经过主题筛选的采集结果或来源检查状态。
- `cbok.notification` 已有 Django 邮件后端，可以复用 SMTP 配置和发送实现。
- `cbok.batch.BatchProcessor` 的周期线程捕获了循环变量，增加多个任务前需要修复，否则可能执行错误任务或使用错误间隔。
- 当前自动调度挂在 `manage.py runserver`，不是通用生产 worker。应提供显式运行入口，并防止同一检查项并发执行。
- 本地 G4F 6.7.0 的实测未成功；新的模型抽象不代表它的外部服务已经恢复可用。

## 3. 模块边界

| 机制 | 建议位置 | 负责 | 不负责 |
| --- | --- | --- | --- |
| 来源 | `cbok/alert/sources/` | 来源注册、配置、采集和来源专用解析 | 主题筛选、模型分析、发送通知 |
| 检测 | `cbok/alert/monitoring/` | 观测、预期规则、调度、状态和事件 | 承诺外部站点稳定、猜测新闻价值 |
| 通知 | 复用并扩展 `cbok/notification/` | 通知事件的渠道分发与发送结果 | 判定来源是否变化 |
| 模型 | 将 `cbok/alert/llm.py` 整理为兼容原导入方式的模块/包 | 配置项解析、后端注册、统一调用、结果及错误转换 | 采集调度、未经配置的自动付费切换 |

上述目录名和实现细节是设计建议，用户尚未逐项指定。

## 4. 来源机制

来源分为两层：数据库中的配置实例和代码适配器。Source 记录来源类型与适配器；Section 记录板块/资源、地址和参数；Check 记录使用的检测脚本、规则参数、间隔和异常策略。它们都是可枚举的数据库记录，不能只在代码或配置文件中维护腾讯板块。适配器注册表使用明确名称。

来源统一提供：

1. 采集：接收板块/资源、数量上限及可选游标，返回归一化条目和分页信息。
2. 读取详情：按适配器返回的条目标识读取详情；标识不必是 HTTP URL。
3. 观测：为检查条目取得观测数据和证据，交给通用检测器。

归一化条目包含来源 ID、外部 ID、内容类型、可选标题/地址/时间、数据载荷及元数据。网页、HTTP API、RSS 等是适配器内部的取数方式；未来其他类型无需实现 HTML 选择器或伪造 HTTP 状态码。

腾讯适配器同时处理页面壳、JSON 列表和内容页。检测与实际采集复用相同的请求构造和解析函数，避免检测通过而采集代码已经失效。

采集结果使用独立的来源条目存储，以 `(source_id, external_id)` 幂等更新；本次不强制关联 Topic，也不更改旧 Article 的唯一性规则。原始大响应仅保留必要的有界诊断片段，避免持续保存整个页面。

首版手动采集有数量上限。周期检测只做所需的列表请求和有限内容页抽样，不自动抓取所有历史内容，不触发模型调用。

## 5. 腾讯首批板块及预期

2026-10-23 使用少量、无登录请求验证，临时绕过了失效的本地代理，保留 TLS 证书验证。

| 板块 | 页面 | 列表接口 | 当前关键差异 |
| --- | --- | --- | --- |
| 要闻 | `https://news.qq.com/` | POST `https://i.news.qq.com/web_feed/getHotModuleList` | `channel_id=news_news_top`；成功响应有 data，但没有 code |
| 财经 | `https://news.qq.com/ch/finance/` | POST `https://i.news.qq.com/web_feed/getPCList` | `channel_id=news_news_finance`；成功时 code=0 |
| 科技 | `https://news.qq.com/ch/tech/` | 同财经接口 | `channel_id=news_news_tech`；成功时 code=0 |

这些是网站当前使用的接口，未找到公开的兼容性承诺。

公共身份准备接口为 GET `https://i.news.qq.com/web_backend/getWebPacUid`，当前需要 `code=0` 且 `data.pac_uid` 是非空字符串，前端将其用于 `qimei36/device_id`。

列表请求参数以官方页面引用的 channel.js 为依据，包含 base_req、forward、qimei36、device_id、flush_num、channel_id 和 item_count；财经、科技另有 is_local_chlid。此身份仅是公开匿名请求流程，不代替登录或访问控制。

建议配置以下检测项，允许单独启停和调整间隔：

- 页面壳：状态、HTML 类型、`window.channelInfo` 可解析、channelKey 符合对应板块。当前页面初始 `#root` 为空，不能把静态新闻链接非空作为规则。
- 列表接口：JSON 可解析、来源声明的成功条件、data 类型和新闻提取结果。财经/科技检查 code=0，要闻不要求不存在的 code 字段。
- 列表条目：普通条目检查稳定标识、标题和可用链接；包装模块通过 sub_item 展开，链接从 link_info.url 取得。允许额外字段和非新闻模块，不要求每个顶层条目都是文章。
- 抽样详情：从本轮有效条目中选取一篇普通文章，跟随受限的站内重定向，检查文章标题、正文区域和必要元数据能被同一解析器提取。视频/专题等类型独立识别，不能用纯文本文章契约强行检查。

正常标题、顺序、条目数量、发布时间和正文更新不构成结构变化。列表非空是可配置的业务预期，空列表单独报告为 EMPTY_RESULT，不能仅凭它断言页面结构已改。

## 6. 通用检测机制

一个来源可以有任意多个板块，每个板块可以配置多个检查项。每项在数据库中保存稳定 ID、脚本名称、规则参数、预期、间隔、启停状态与通知策略。

### 6.1 集中异常目录

所有业务异常类型在 alert 检测模块的集中目录中声明，可完整枚举并同步到数据库 AnomalyType 表。例如初期包含 SECTION_CHANGED、NETWORK_ERROR、ACCESS_ERROR、EMPTY_RESULT、CHECK_EXECUTION_ERROR 和 CHECK_CONFIG_ERROR。每条声明包含稳定 code、名称、含义和默认策略；业务类型不采用数据库原生 ENUM，也不要求每次新增类型生成数据库迁移。

新增异常类型只在集中目录加一条定义；检测脚本返回该 code，通用框架通过目录和数据库策略处理，禁止按每一种业务 code 写 if/elif 分支。未知 code 是脚本协议/配置错误，不能静默丢弃。目录同步保持幂等，并保留管理员在数据库中调整过的策略。

### 6.2 检测脚本协议

检测方式通过独立脚本提供。每个插件由一个声明文件和一个脚本组成，目录扫描自动发现；添加插件无需修改框架或中央 import 列表。首版使用 Python 脚本，并保留独立进程、标准输入/输出的协议边界。

- 声明文件说明检测器稳定名称、协议版本、入口脚本、超时及参数约束。
- 输入是 JSON：协议版本、执行 ID、来源/板块/检查项标识及所需配置、规则参数。
- 输出是一个 JSON 结果：执行是否成功、检查是否通过，以及 issues 数组。每个 issue 有异常类型 code、稳定 rule_id、摘要、expected/observed 和有界证据。
- 正常业务异常通过 issues 返回，不借助非零退出码冒充；脚本崩溃、超时、协议版本错误、无效输出由框架转换为已登记的执行异常。
- 标准错误用于诊断日志；限制运行时长和输出大小。仅执行管理员部署的插件目录内脚本，不使用 shell 拼接命令。
- 来源专用细则写在检测脚本或脚本共用的解析/规则辅助模块内；腾讯脚本复用实际采集的适配器解析器。

公共脚本初期覆盖 HTTP/JSON/HTML 契约；腾讯可增加更细的包装条目和内容页规则。规则仅改变已有脚本支持的参数时，只增加/修改数据库检查记录；需要新的判断逻辑时，只新增脚本及声明文件。

### 6.3 观测与结果

观测与判定分离：观测对象包含获取状态、数据格式、数据、采集时间、证据位置和有界诊断信息。规则读取这些字段，不直接依赖 requests.Response。

检查结果至少区分：

- PASS：成功取得观测，必需契约符合预期。
- CONTRACT_FAILED：取得了可判断的数据，必需字段、类型或解析契约不满足预期。
- UNAVAILABLE：网络超时、DNS/TLS、HTTP 403/429/5xx、登录页或访问限制等，不能判断结构是否变化。
- CONFIG_ERROR：配置或规则不合法，单独暴露原因，不伪装成上游变化。

EMPTY_RESULT 等具体原因保留在结果中。未满足可选的“列表必须非空”预期可以触发对应异常，但文案只陈述实际证据。

不比较整页 HTML 哈希，也不把所有异常统称“结构变化”。检测规则的预期随配置版本明确管理，不能在失败后自动接受新结果作为健康基线。

## 7. 状态、告警与通知

数据库是业务配置和运行状态的权威来源：Source、Section、Check、AnomalyType、CheckRun、Incident 和 NotificationDelivery 分别保存来源、板块、检测配置、异常目录、每次运行、活动异常和投递记录。通知渠道和模型配置项也以数据库记录表示；凭据仅保存环境变量引用，SMTP 参数沿用现有 CBoK 配置。重启后延续状态。

依据用户本轮补充，板块变化和网络异常都必须记录数据库并通知管理员。每次检测结果和异常都会立即落库，不能因为通知阈值未到而丢弃异常记录。首版默认首次异常即产生管理员通知，同一持续异常去重；确认恢复时通知。通知阈值、是否重复提醒和恢复通知按异常类型配置，可由检查项覆盖。此前“连续三次”的建议未获确认，不作为固定行为。网络/访问不可用和契约失败分别表述；不可用不会把既有契约异常误标为恢复。

去重键不包含本次新闻标题、时间戳等高频变化值。按来源、检查项、配置版本、异常类别和失败规则 ID 集合识别异常；事件实例有独立 ID，同一异常恢复后再次出现会创建新的事件。配置版本变化不会沿用旧规则的连续失败次数。

通知采用统一事件：事件 ID、类型、来源/检查项、期望与实测、首次及最近发生时间、证据位置和恢复信息。渠道配置指定收件人等目标，不沿用代码中写死的邮箱。

先持久化事件与待发送记录，再调用渠道；只有渠道确认发送才记录成功。失败保留待重试状态，设置可配置退避上限，避免丢信或每轮无限重复。唯一投递记录减少并发重复；SMTP 不提供严格端到端恰好一次，进程在发送后、落库前崩溃仍可能重复，这一限制需明确。

过时投递的具体处理是本设计提出的默认行为：按渠道记录首条告警是否投递成功；如果尚未成功告警便已恢复，取消该渠道待发送的旧告警，也不向它发送无上下文的恢复邮件。已经成功收到告警的渠道才产生对应恢复投递。待投递的恢复消息遇到新的活动异常时取消，后续发送新的当前状态，避免先发新告警、后发过时恢复。配置版本变化将旧事件标记为被替代并取消旧待投递记录，不把更改配置本身说成健康恢复。

首版只实现邮件渠道，复用现有 Django SMTP 后端；之后新增渠道只需适配事件发送接口。未配置目标时不发送真实邮件，保留可查询事件和明确日志；启用某渠道时才校验其必需配置。

## 8. 周期任务与入口

复用现有周期任务发现机制：增加一个扫描到期检查项的入口，各检查项按配置间隔调度。修复 BatchProcessor 的循环变量捕获问题，并覆盖两个独立周期任务的执行测试。

每次执行单项隔离，某一板块失败不阻断其他检查。数据库租约防止同一检查项并发运行，租约带过期时间以便异常退出恢复；成功和失败都释放租约。定时调度使用时间间隔，不做重叠执行。

提供显式 worker 入口，以便不依赖 runserver 副作用；保留现有开发启动兼容，不在应用导入、迁移、CLI --help 或单纯读取配置时启动任务。实际开启检测由配置控制。

提供手动采集及单轮检查入口。手动检查默认是独立验证：仅输出/记录本次观测，不修改正式连续计数、事件、恢复状态或下次周期执行时间，也不创建待发送记录，因而后续 worker 不会替它补发邮件。显式的应用选项才让本轮结果参与正式状态机；显式通知选项同时要求应用选项，并按正式策略投递。这个命令语义是本设计提出的默认行为。按项目 CLI 约定提供 --help、返回码和错误信息。

## 9. 模型机制

模型配置项使用独立名称：后端、模型名、可选后端 provider、base_url、凭据环境变量名、超时和 JSON 输出要求。

- G4F 后端：按配置选择 provider/model，延迟导入；缺少认证、服务不可用等明确失败，不能当成有效回答。
- DeepSeek 后端：复用 OpenAI 兼容协议，但模型、地址与凭据不写死在业务代码中。
- 其他 OpenAI 兼容后端：配置 base_url、model 和凭据引用即可；非兼容协议通过注册新的适配器实现。

统一调用接受消息与输出约束，返回文本和可用的模型/provider 元信息；可将结构化输出再交给调用方验证。不同后端不能声称具备未验证的 JSON Schema 等能力，必要时返回能力不支持。

只初始化实际选择的后端。未使用 DeepSeek 不要求其 key；未配置模型不阻塞来源采集和检测。没有显式选择模型时，模型调用返回配置错误，不默认调用付费服务。禁止把 G4F 失败自动转成 DeepSeek 等付费调用。

保留原有导入路径的兼容导出；旧 DeepSeek 凭据可作为显式 DeepSeek 配置项的兼容读取。旧主题接口的模型选择改为工厂创建，但不在本次把腾讯来源接入旧主题推理流程。

## 10. 配置与落地建议

继续以 cbok.conf 为 CBoK 启动入口；来源、板块、检查项、异常策略、通知渠道和模型配置项以数据库为准。独立 TOML/JSON 文件用于首次初始化、示例导入和插件声明，不作为第二份实时权威配置。Python 3.12 自带 tomllib，无需引入配置解析依赖。

配置文件路径相对实际 CBOK_CONF 文件解析；配置内资源路径再相对该文件解析。非 master worktree 显式设置 CBOK_CONF。示例配置不包含真实 key、账号或收件人。

初始化内容包括 `sources[]`、`sections[]`、`checks[]`、`anomaly_types[]`、`notification_channels[]`、`model_profiles[]` 和调度默认值。导入/目录同步保持幂等，不覆盖管理员已有配置；明确的更新操作才能替换已有配置。提供枚举来源、板块、检查脚本、规则/异常目录及其启停状态的入口。启用的对象引用必须可解析，ID 唯一，适配器与检测脚本须已登记；禁用的可选功能不要求其外部凭据。

对重复 ID、未知适配器、无效间隔、无效 JSON 路径等给出明确配置错误；不得静默跳过所有检查并报告健康。

本仓库当前忽略 app migrations，新增持久化模型时需要把对应迁移纳入交付，并明确迁移命令；不运行现场数据库迁移，不更改已有无关数据。

## 11. 验证与验收

新增测试统一在 `cbok/test/` 下。至少验证：

1. 腾讯三种列表/包装条目和文章详情能够提取；正常新闻变化不告警。
2. 删除必需字段、改变数据类型、返回错误页面后，相关检查按契约失败或不可用正确分类；额外字段不误报。
3. 超时、403、429 与结构失败不同；不可用不会误发恢复。
4. 多检查项独立运行；连续异常阈值、去重、恢复、重启后状态延续和通知失败重试。
   同时覆盖手动验证不影响正式计数/待投递记录，及已恢复/已被配置替代的旧告警不会延迟发送。
5. 两个周期任务不会互相串函数/间隔；同一检查项不会并发重入。
6. 显式模型配置选择不同后端；未选择的后端不导入、不索取 key；G4F 失败不调用 DeepSeek。
7. 手动采集/检查入口及 --help 可用；检查默认不发送真实通知。
