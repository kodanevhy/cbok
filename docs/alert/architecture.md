## 现有实现

```text
POST /alert/topic/
  -> TopicView 创建 Topic，并启动初始化线程
  -> AlertManager
       -> GoogleAlertCrawler：查询话题历史，抓取文章
       -> Article：保存文章
       -> DeriveContext + Deepseek：从文章提取问题、回答
       -> Question / Answer：保存推理结果
       -> EmailService：发送话题初始化邮件
```

入口在 [views.py](../../cbok/alert/views.py)，编排在
[manager.py](../../cbok/alert/manager.py)，持久化结构在
[models.py](../../cbok/alert/models.py)。
抓取、模型和邮件在 `AlertManager` 初始化时绑定，
不适合作为“只检查一个接口”的入口。

[gate.py](../../cbok/alert/gate.py) 中的周期处理仍是占位逻辑；
不能把现有话题初始化流程描述成已经完整运行的持续监控服务。

## 框架设计

### 主链路

```text
注册配置 -> 数据库中的 Source / Section / DetectorCheck
                         |
                  显式启动的 worker
                         |
                   领取到期检查项
                         |
             独立检测进程 -> 来源适配器
                         |
                 观测 + 确定性规则
                         |
                      CheckRun
                         |
                Incident 状态机与去重
                         |
             NotificationDelivery 待投递记录
                         |
                  通知渠道 -> 用户
```

采集和检测都可以使用来源适配器，但不相互隐式触发：
采集负责保存内容；检测只获取判断所需的观测，决定是否存在异常。
模型分析是独立能力，不是每次检查的必经步骤。

### 模块职责

以下路径是 #128 中的实现草案位置，不是当前 master 的可用模块列表。

| 层 | 草案位置 | 负责 | 不负责 |
| --- | --- | --- | --- |
| CLI | `cbok/cmd/alert.py` | 注册、枚举、手动采集、检查和启动 worker | 来源解析、直接发送邮件 |
| 来源 | `cbok/alert/sources/` | 请求外部来源，归一化条目和观测 | 调度、事件状态、通知 |
| 检测 | `cbok/alert/monitoring/` | 规则、插件协议、执行边界、结果校验 | 猜测用户兴趣、选择通知渠道 |
| 运行编排 | `monitoring/service.py` | 到期调度、租约、检查记录、事件及投递状态 | 实现具体网站的解析器 |
| 通知 | `cbok/notification/channels.py` | 按渠道发送统一消息，报告成功或失败 | 判断来源是否异常 |
| 模型 | `cbok/alert/llm.py`、`model_profiles.py` | 显式选择模型并调用 | 自动轮询、免费后端失败后转付费 |

来源适配器提供 `collect`、`read`、`observe`：
分别用于有界采集、读取条目详情、获取检查观测。
网页、HTTP API 等取数方式封装在适配器里，框架不依赖某个网站的 HTML。
实际采集与检查应复用相同解析逻辑，避免“检测通过，但采集已坏”。

### 配置与数据

| 记录 | 含义 |
| --- | --- |
| `Source` | 一个来源实例：适配器、配置、启停及关联通知渠道 |
| `Section` | 来源下的板块或资源，例如腾讯财经 |
| `DetectorCheck` | 一个检查项：检测器、规则、间隔、租约和配置版本 |
| `AnomalyType` | 异常分类及通知策略，和 Python 异常类不是同一概念 |
| `CheckRun` | 每一次检查的结果、证据和执行时间 |
| `Incident` | 持续异常的生命周期、次数和恢复状态 |
| `NotificationChannel` | 通知渠道实例及收件目标 |
| `NotificationDelivery` | 某事件向某渠道的待发、重试、成功或取消记录 |
| `CollectedItem` | 按来源和外部 ID 去重的采集内容，不强制关联 Topic |
| `ModelProfile` | 模型后端、模型名、超时及凭据环境变量引用 |

业务配置和运行状态以数据库为准。JSON/TOML 导入文件只负责初始化或显式更新，
不成为第二份实时配置；普通重复注册保留管理员的修改。
代码中的注册表定义“有哪些能力”，数据库记录选择“启用哪些实例”。
新增实现只进入对应注册表，不能从数据库任意导入 Python 路径。

密钥不得写进文档或提交到仓库，凭据通过环境变量等受控方式提供。
新监控链路不复用旧 `Article` 的 Topic 外键和全局 URL 唯一性约束。

### 检测与 AI 的边界

“有变化”至少有三种含义，不能混成一种检查：

| 场景 | 判断方法 | 状态 |
| --- | --- | --- |
| 必需字段消失、类型错误、正文解析失效 | 声明式契约，例如 required、type、html_selector | #128 覆盖 |
| 库存从 0 变成有货、某状态字段改变 | 比较指定字段或命中业务条件 | 后续增加检测器和状态定义 |
| 新闻是否值得提醒、内容是否与兴趣相关 | 确定性筛选后，显式调用所选模型 | 后续语义分析 |

不能比较整页 HTML 哈希就宣称“网站结构变化”，正常标题、顺序和时间更新
也不应触发契约异常。#128 的契约检查不是任意 JSON 前后 diff 引擎。
业务变化检测还需定义首次样本是否通知、比较字段、基准更新及重复提醒规则。

检测结果统一为 `pass`、`fail`、`unknown`：
可确认不符合预期才是 `fail`；网络超时、访问受限或执行失败等无法完成判断的
情况是 `unknown`，通过异常 code 进一步分类，不能误报为结构变化或健康恢复。

检测插件由 `manifest.toml` 和脚本组成，通过标准输入/输出交换版本化 JSON。
执行器限制时间与输出大小，校验 status、issues 和异常 code。
脚本不直接操作应用数据库、不发送通知、不调用模型。
独立进程提供超时和故障隔离，**不是安全沙箱**；只运行管理员信任的插件。

### 调度与事件

worker 按检查项间隔领取到期任务，用有期限的数据库租约避免同项并发运行。
#128 的单个 worker 顺序执行；扫描间隔不等于每项准确的开始时间，
某项失败不应阻断其他项。导入模块、查看帮助和执行迁移都不能自动启动监控。

手动检查区分三个模式：只记录 `CheckRun`；显式应用到事件状态机；
显式应用并允许通知。只采集不调用模型，也不通知。
检查发现异常与命令执行失败分开表达，不以 CLI 退出码代替检测结果。

每次检查都留记录，同一配置版本、异常类别和失败规则的持续异常复用同一事件。
默认首次异常通知，持续异常不重复创建首报；阈值和恢复通知由策略决定。
网络未知不能确认原有契约异常已经恢复；配置变化使旧事件被替代，不是恢复。

通知先写入待投递记录，再调用渠道；发送失败保留错误并退避重试。
恢复或配置替代时取消未开始的过时投递；已经收到告警的渠道才需要恢复消息。
发送已在进行时需协调租约、确认和恢复状态，不能仅删掉队列记录。
发送成功但落库前进程崩溃可能导致重发，因此不承诺端到端恰好一次。
租约也不能中断阻塞的网络调用，渠道本身必须设置超时。

### 腾讯示例

#128 默认登记一个腾讯来源，包含要闻、财经、科技三个板块；
每个板块分别检查 page、feed、article，共九项。
page 检查页面壳，feed 检查列表契约，article 有界抽样详情。
不同接口的成功条件分别配置，不把要闻和财经的响应结构强行统一。

例如 feed 的必需字段失效：适配器获取观测，检测器返回具体规则失败，
框架保存 `CheckRun`、创建或更新 `Incident`，再按策略产生邮件投递。
下一次相同失败更新原事件；确认正常后处理恢复。
整个过程不需要 Google 登录，也不需要调用模型。
默认注册不替用户配置真实收件人或付费模型。

## Web Push 扩展

Web Push 应作为通知渠道接入，不应让检测器直接联系 iPhone：

```text
iPhone 从主屏幕打开 HTTPS 订阅页
  -> 用户授权 -> PushSubscription -> 保存订阅

常驻监控 -> Incident -> NotificationDelivery
  -> Web Push 渠道 -> 苹果推送服务 -> iPhone 系统通知
```

订阅需保存完整的 endpoint 与加密参数，VAPID 密钥需持久保存，
私钥只留在发送端。还需实现订阅接口鉴权、取消订阅和失效订阅清理。
推送服务接受请求不等于已确认用户设备显示通知。

HTTPS 页面可以托管在固定地址；实际监控程序可以运行在可访问内网接口的机器，
不必把被监控接口暴露到公网，也不要求接口本身是 HTTPS。
iPhone 负责接收系统推送，不依靠网页在后台轮询。
临时测试页、手动延时通知和免费临时隧道都不是长期监控部署。

这些是后续接入要求，#128 目前只实现邮件渠道，不包含 Web Push、
订阅页面或通用业务字段变化检测。
